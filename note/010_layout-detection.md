# 010 レイアウト検出

## 1. 目的

ページの中の段落を、本文、図の中の文字、表の中の文字、独立した数式、参考文献などに区別します。
訳す段落と、原文のまま残す段落を決めるために使います。
文字の位置だけでは、図や表の中の文字と本文を区別できません(`note/009_pdf-view.md` の「見つかった誤り」)。
計画のマイルストーン M3 に当たります。

## 3. 設計判断

### モデルと実行ソフト

- モデルは、PaddlePaddle が Hugging Face で公開している ONNX 形式の PP-DocLayoutV3(`PaddlePaddle/PP-DocLayoutV3_onnx`、Apache-2.0、130,502,049 バイト)を使います。
- 実行には、Microsoft の `onnxruntime-web` を直接使い、前処理と後処理は自分で書きました。PP-DocLayoutV3 をブラウザで動かす npm パッケージ(`web-sdk-pp-doclayoutv3`、`ppu-doclayout`)は使っていません。前処理と後処理は合わせて 100 行ほどで済み、個人が公開しているパッケージへの依存を増やさずに済むためです。`ppu-doclayout` は、説明に PP-DocLayoutV2 用と書かれていました。
- モデルのファイルは、リポジトリに含めず、ブラウザが Hugging Face から取得します。取得する URL は、リポジトリの版(コミット `46bbdf1`)を固定しています。取得したファイルは SHA-256 を計算し、コードに書いた値と一致した場合だけ使います。
- 取得したファイルは、ブラウザの Cache Storage に保存し、2 回目以降は取得しません。保存先は、Web アプリの URL(オリジン)ごとに分かれます。
- 検出は、利用者がボタンを押してから始めます。130 MB の取得が、PDF を開いただけで始まらないようにするためです。

### 前処理と後処理

- 入力は、モデルの設定ファイル `inference.yml` の `Preprocess` に合わせました。ページの画像を、縦横比を保たずに 800×800 画素へ縮め、画素の値を 0 から 1 にし、RGB の順に色ごとに並べます。
- `inference.yml` は、縮めるときの補間に `interp: 2` を指定しています。こちらは、ブラウザの `createImageBitmap` の高品質の縮小を使っており、補間の方法は一致していない可能性があります。色の並び(RGB か BGR か)と、値を 255 で割ることは、`inference.yml` からは読み取れなかったため、推測で決めました。見本の 2 本では、目で見て妥当な結果が出ています。
- モデルの入力は 3 つ(`image`、`im_shape`、`scale_factor`)あります。`scale_factor` に 1 を渡し、出力の座標を 800×800 の画素で受け取ってから、ページの座標(ポイント)に換算しています。
- モデルの出力は 3 つあります。そのうち、1 行が 7 つの数値でできた表を、領域の一覧として読みます。7 つの数値は、種類の番号、確からしさ、左、上、右、下、読む順番と解釈しました。この解釈は、出力を画面に重ねて、種類の名前と枠の位置が紙面と合うことで確かめました。配布元の説明で確かめたものではありません。
- 7 つ目の数値(読む順番)は、連続した番号ではなく、21、65、81 のような飛び飛びの値でした。紙面の上から下、左の段から右の段の順に大きくなっていたため、並べ替えの鍵として使っています。
- 確からしさが 0.5 未満の領域は捨てます。`inference.yml` の `draw_threshold` と同じ値です。
- 出力のうち、残りの 2 つ(領域の数と、領域の形を表すとみられるもの)は使っていません。

### 段落への種類の割り当て

- 検出した領域の矩形は、段落の矩形としては使いません。段落の矩形は文字の位置から作り(`note/009_pdf-view.md`)、検出の結果からは種類だけを取ります。
- 段落の面積の半分以上を覆う領域のうち、最もよく覆うものの種類を、その段落の種類にします。同じ程度(差が 0.05 以内)に覆う領域が複数ある場合は、小さい領域を選びます。図の領域の中に、説明文の領域が入っている場合に、内側の種類を採るためです。
- どの領域も半分以上を覆わない段落は、種類を `unknown` にします。
- `inline_formula`(文中の数式を囲む小さな領域)は、段落の種類の候補にしません。
- 訳す種類は、計画の表のとおり、`text`、`abstract`、`doc_title`、`paragraph_title`、`figure_title`、`footnote`、`vision_footnote` の 7 つです。それ以外と `unknown` は訳しません。迷う段落を訳さない理由は、誤って訳すと元の情報が消えるためです。
- この区別は、いまは枠の表示(青い実線と灰色の破線)に使うだけです。翻訳は、まだ呼び出していません。

### スレッド用の応答ヘッダー

- WebAssembly を複数のスレッドで動かすには、ページが `Cross-Origin-Opener-Policy: same-origin` と `Cross-Origin-Embedder-Policy` の 2 つの応答ヘッダーを持つ必要があります。後者は `credentialless` にしました。arXiv と Hugging Face からの取得と、llama-server への依頼は、認証情報を送らないため、この指定で妨げられません。
- 最初は Vite の `server.headers` で指定しましたが、PDF.js のワーカーが起動しなくなり、PDF.js が画面のスレッドで PDF を解釈する状態(コンソールに `Setting up fake worker` と表示)になりました。原因は、Vite が「変更なし」(HTTP 304)の応答にこのヘッダーを付けないことでした。ブラウザは、ヘッダーを足す前に保存したワーカーのスクリプトを使い続け、ヘッダーが無いスクリプトとして読み込みを拒みました。
- そのため、304 を含むすべての応答にヘッダーを付ける処理(`vite.config.ts` の `isolationHeaders`)に変えました。変えたあと、ワーカーが起動することを確かめました。

## 4. 動作確認

環境は、macOS 26.6(Apple M5、メモリ 24 GB)、Node.js 26.13.1、Chrome、`npm run dev` です。
見本の PDF は、arXiv の 1512.03385(2 段組、12 ページ)と 1706.03762(1 段組、15 ページ)です。

- `npm test`: 162 件すべて成功。
- `npm run build`: 成功。`dist/ort/` に WebAssembly のファイルが複製されました。`dist/` 全体は 124 MB で、そのうち `dist/ort/` が 90 MB です。
- モデルの取得: Hugging Face から取得でき、ハッシュ値が一致しました。同じファイルを `curl` でも取得し、SHA-256 が配布元の表示(`45bf7175…`)と一致することを確かめました。

### 処理時間

1512.03385 の 12 ページを、倍率 150% で表示して検出しました。
時間は、ワーカーの中での前処理から、出力を取り出すまでです。ページの画像を 800×800 に縮める時間は含みません。
測定は、それぞれ 1 回です。

| 実行の方法 | ページ数 | 中央値(ミリ秒) | 最大(ミリ秒) |
| --- | ---: | ---: | ---: |
| WebGPU | 12 | 257 | 442 |
| WebAssembly(8 スレッド) | 12 | 951 | 1,077 |

- WebGPU は、別の回に、最初の 1 ページで 1,590 ミリ秒かかりました。モデルを読み込んだ直後の準備の時間が含まれると推測します。
- 1706.03762 では、WebGPU で 13 ページを検出し、中央値 209 ミリ秒、最大 414 ミリ秒でした。
- 計画の合格の目安は「1 ページあたり 1 秒未満」です。WebGPU は目安を満たしました。WebAssembly は、中央値は満たし、最大は超えました。
- この結果から、WebGPU を既定にし、PP-DocLayoutV3 を採用します。軽量なモデルへの切り替えは行いません。

### 検出の結果(目視)

- 1512.03385 の 1 ページ目: 題名(`doc_title`)、要旨(`abstract`)、節の見出し(`paragraph_title`)、本文(`text`)、図(`chart`)、図の説明文(`figure_title`)、脚注(`footnote`)、ページ番号(`number`)、左端の縦書きの arXiv の表示(`aside_text`)が検出されました。図の中の目盛りと凡例は「訳さない」になりました。
- 1706.03762 の 6 ページ目: 表(`table`)の中の文字と、独立した数式(`display_formula`)が「訳さない」になり、表の説明文(`figure_title`)、節の見出し、本文が「訳す」になりました。
- 1706.03762 の 10 ページ目以降で、参考文献(`reference`、`reference_content`)が検出されました。枠の表示は目で見ていません。

### 見つかった誤り

- 1512.03385 の 1 ページ目の要旨の次の段落(本文)が、`abstract` と検出されました。どちらも訳す種類なので、訳すかどうかには影響しません。
- 同じページの著者の名前(4 人)は、どの領域にも当たらず `unknown` になりました。所属(`Microsoft Research`)とメールアドレスは `text` と検出され、「訳す」になりました。計画では、題名と要旨の間にある段落を訳さない規則で扱う予定で、まだ作っていません。

### 未確認

- `npm run build` で作ったファイル(`npm run preview`)での検出。
- WebGPU が使えないブラウザでの動作。WebGPU を選んで失敗した場合に、WebAssembly へ自動で切り替える処理はありません。
- スレッド用の応答ヘッダーが無い場合(1 スレッド)の WebAssembly の処理時間。

## 5. 注意点・残課題

- 初回は、検出モデルのファイル(130.5 MB)を Hugging Face から取得します。
- `dist/` の内容を別のサーバーで配る場合は、そのサーバーで 2 つの応答ヘッダーを設定する必要があります。設定しないと、WebAssembly は 1 スレッドで動きます。
- 計画では「検出が使えない環境でも、規則だけで種類を判定して動く」としています。規則だけの判定は、まだ作っていません。検出を有効にしていない間は、段落に種類が付きません。
- 計画では、検出の結果を「PDF の識別子、ページ番号、検出器の版」で保存するとしています。保存は、まだ作っていません。ページを読み込み直すと、検出をやり直します。
- 検出は、通常の描画が終わったページを、描画の倍率のまま入力にしています。倍率によって結果が変わるかは確かめていません。
